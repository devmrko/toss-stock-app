# 설계서: 하루 급등+실적직결 촉매 없음 조합은 당일 매수 보류 (#838)

> **상태**: Approved
> **작성**: [AI] Architect · **최종수정**: 2026-10-07
> **추적성** — Redmine: #838 · 관련 ADR: 없음
> · 구현 파일: `AutoTradeScheduler.java`(수정), `AutoTradeProperties.java`(필드 추가) ·
>   테스트: `AutoTradeSchedulerTest`(추가)

## 1. 목적 (Why)
사용자 논의(2026-10-07, 053800/안랩 실사례): 하루 만에 +13.3%(종가 기준)~+18.2%(장중 피크
기준) 튄 종목을 그날 바로 사는 게 맞는가. 결론: 하루 변동폭의 **크기**와 **촉매의 종류**를
같이 봐야 한다 — "해킹 사건 터지니까 보안주 테마로 반사이익" 같은 테마성/감정적 반응은 단기
트레이더가 몰렸다가 빠지며 급격한 되돌림 위험이 크고(실측: 안랩이 다음 거래일 트레일스탑
-10%에 걸림), "AI 데이터센터 냉각설비 5조원 계약" 같은 실적직결형 사건은 되돌림 압력에도
바닥을 지킬 가능성이 높다.

## 2. 범위 (Scope)
- **포함**: `AutoTradeScheduler.scanCandidates`에 새 보류 조건 추가 — 당일 가격변동률이
  임계값(기본 8%) 이상이면서 동시에 `CapitalReturnCatalystDetector.hasRecentCatalyst`(실적직결
  촉매)가 false면, 그 틱에서는 매수하지 않고 넘어간다.
- **재사용(신규 로직 최소화)**: 두 신호 다 이미 존재 — `PopularityChecker.priceMovePct`(#832에서
  이미 추가된 수치 추출 함수)와 `CapitalReturnCatalystDetector.hasRecentCatalyst`(#808 §11,
  이미 "수주/계약/증설/투자/배당/자사주/호실적" 등 키워드로 실적직결형을 구분). 새 분류 로직이나
  LLM 호출을 추가하지 않는다.
- **제외 (out of scope)**: 뉴스 분류 파이프라인(`NewsClassifier`)에 "테마성/실적직결형" 라벨을
  신설하는 것 — 기존 `CapitalReturnCatalystDetector`의 키워드 매칭을 그대로 재사용하는 쪽이
  훨씬 적은 변경이고 이미 같은 목적(재평가 여지 판단)으로 검증된 신호라 그쪽을 선택(§11).
- **보류 기간을 명시적으로 추적하지 않음**: "하루 쉬고 안정화 확인 후 매수"를 날짜 카운터로
  구현하지 않는다 — 오늘 조건(당일 변동폭 극단적+촉매 비실적직결)에서만 매수를 막으면,
  다음날 그 "당일 변동폭"이 자연히 작아지므로(어제 일은 더 이상 "오늘 변동"이 아님) 날짜를
  추적하지 않아도 저절로 "하루 지나면 재평가"가 된다(§8).

## 3. 인수조건 (Acceptance Criteria)
- [ ] 당일 가격변동률 ≥ extreme-move-pct(기본 8%) AND 실적직결 촉매 없음 → 그 종목은 그 틱에서
      매수 보류(계속 후보로는 남음, 다음 틱/다음날 재평가).
- [ ] 당일 가격변동률 ≥ 8%라도 실적직결 촉매가 있으면(예: 066570 사례) 보류하지 않고 정상 매수
      진행(기존 동작 유지).
- [ ] 당일 가격변동률 < 8%면 이 조건과 무관하게 기존 로직 그대로.
- [ ] 거래량 스파이크만으로 "인기" 판정된 경우(가격은 안 움직이고 거래량만 튄 경우)는 이 조건의
      대상이 아님 — "가격"이 당일 급등한 경우만 본다.
- [ ] 기존 테스트 전부 통과 + 신규 케이스(임계값 이상+촉매없음 → 보류, 임계값 이상+촉매있음 →
      매수) 테스트 추가.

## 4. 컨텍스트 & 제약
- 의존성: 없음(신규 외부 I/O 없음) — `scanCandidates`에서 이미 계산된 `recent`(일봉)와
  `rerateCatalyst`(이미 호출된 `hasRecentCatalyst` 결과)만 재사용.
- 제약: `PopularityChecker.priceMovePct`는 "최신 거래일 종가 vs 전일 종가"만 본다(장중 피크는
  안 봄) — 안랩 사례의 "장중 피크 +18.2%"가 아니라 "종가 +13.3%"가 실제로 쓰이는 수치. 그래도
  8% 기준선은 넉넉히 넘으므로 판정에는 영향 없음.
- 가정: 8%라는 숫자는 실측 1건(안랩 +13.3%)에 기반한 초기값 — 다른 프로젝트 임계값들과 동일하게
  "검증 단계, 운영하며 조정" 대상(§11).

## 5. 아키텍처 개요
```
[AutoTradeScheduler.scanCandidates]
  ... 인기 판정(기존) → 통과
  valuation = getValuation(...)
  cheap = isUndervalued(...)
  rerateCatalyst = hasRecentCatalyst(...)          ← 이미 계산됨, 재사용
  ──────────────── 신규 ────────────────
  todaysMovePct = PopularityChecker.priceMovePct(recent)   ← 이미 있는 함수 재사용
  if (todaysMovePct >= extremeMovePct && !rerateCatalyst) → continue(이 틱 매수 보류)
  ───────────────────────────────────────
  if (!cheap && !rerateCatalyst) → continue(기존)
  ... 펀더멘털 → 매수(기존)
```
- I/O ↔ 순수 로직 경계: 새 조건은 이미 가져온 `recent`/`rerateCatalyst`로만 판단하는 순수
  비교(분기 1개 추가) — 신규 I/O 없음.

## 8. 흐름 / 알고리즘
`scanCandidates`에서 `rerateCatalyst`를 계산한 직후, `PopularityChecker.priceMovePct(recent)`로
당일 변동률(%)을 뽑아 `props.extremeMovePct()`(기본 8.0) 이상이면서 `rerateCatalyst`가 false이면
`continue`(이번 틱 매수 안 함). 후보 자체는 비활성화하지 않으므로 다음 틱/다음 거래일에 다시
평가된다 — 그날 변동폭이 더 이상 "당일 8% 이상"이 아니게 되면(예: 다음날은 변동이 작거나, 다른
이유로 인기 판정) 자연스럽게 보류가 풀린다. 날짜 카운터나 쿨다운 타임스탬프가 필요 없는 이유.

## 9. 엣지케이스 & 에러 처리
- `recent`가 비어있거나 전일 종가가 없으면 `priceMovePct`는 0을 반환(기존 #832 구현) → 이 조건은
  자연히 통과(보류 안 함) — 데이터 부족을 "극단적 급등"으로 오판하지 않음(fail-open 방향이지만,
  이미 다른 게이트들이 fail-closed로 막아주므로 위험 증가 없음).
- 하락(음수) 변동률은 `priceMovePct`가 음수를 반환하므로 `>= extremeMovePct`(양수)를 만족 못 함
  → 이 조건 대상 아님(원래도 하락일은 "가격 트리거"로 인기 판정 자체가 안 됨).

## 10. 테스트 계획
- `AutoTradeSchedulerTest`: (1) 당일 +10% + rerateCatalyst=false → `orderExecutor.buy` 호출 안 됨.
  (2) 당일 +10% + rerateCatalyst=true → 정상 매수(기존 066570류 사례 재현).
  (3) 당일 +3%(임계값 미달) + rerateCatalyst=false → 기존처럼 정상 매수(회귀 확인).

## 11. 리스크 & 대안 검토
- 대안(기각): 뉴스 분류 파이프라인에 "테마성/실적직결형" LLM 라벨 신설 — 더 정교하지만 분류
  파이프라인 변경+재학습 성격의 프롬프트 튜닝이 필요해 범위가 큼. 기존 키워드 매칭
  (`CapitalReturnCatalystDetector`)으로 충분히 근사 가능하다고 판단, 되돌리기 쉬운 결정(나중에
  부족하면 라벨 신설로 이전 가능) — ADR 불필요.
- 리스크: 8% 임계값은 실측 1건 기반 초기값 — 너무 낮으면 정상적인 모멘텀 종목까지 보류될 수
  있고, 너무 높으면 의도한 필터링이 거의 안 걸림. 운영 데이터 쌓이며 조정 필요(다른 #808
  임계값들과 동일한 처지).
