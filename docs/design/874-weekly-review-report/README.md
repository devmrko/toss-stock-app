## 1. 분석 결론 — **거래 주기는 바꾸지 않는다**

원칙 §0: "**주 1회 점검·거래**로 감정 배제" / §6: "**룰대로** 매수/매도 실행(주 1회)".
봇의 분당 틱과 어긋나 보이지만, **주기를 늘리는 것은 오히려 원칙을 더 크게 위반한다.**

### 1.1 명시된 목적은 '감정 배제'다

§0 원문이 목적을 적어 두었다 — **"감정 배제"**(to keep emotions out). 이는 **사람 고유의
이유**이고 봇은 구조적으로 룰 기반이다. §6 도 핵심은 "**룰대로** 실행"이다.
**수단(주 1회)이 아니라 목적(룰대로·감정배제)이 조항의 내용**이다.

### 1.2 과잉매매의 실제 원인은 주기가 아니라 NEWS_FADED 였다

전체 청산 이력 실측:

| 사유 | 건수 | 비율 |
|------|------|------|
| `NEWS_FADED` | 51 | **94%** |
| `TRAIL_STOP` | 2 | 4% |
| `HARD_STOP` | 1 | 2% |

10/07 하루에 매수 49·매도 48·수수료 64,754원. 회전율 폭주는 분당 틱 때문이 아니라
**8시간 TTL 만료 매도** 때문이었고, **#871 이 그 구조를 제거**했다.

§7 '흔한 실수' 목록에 **과잉매매는 없다** — 손실 키움/물타기/차트의존/과분산/감정매매
다섯이고 전부 이미 구현으로 대응돼 있다.

### 1.3 주기를 늘리면 §0 의 **첫 항목**이 깨진다

§0 의 첫 규칙은 "진입가 −10% 손절, 추적손절 −10%"다. 손절은 **분 단위 감시**가 필요하다.
주 1회 틱으로 바꾸면 −10% 를 한참 지나서야 팔게 되어, **더 중요한 원칙을 희생해 덜
중요한 수단을 맞추는** 결과가 된다.

### 1.4 물타기 금지는 이미 코드로 보장된다

`AutoTradeScheduler.scanCandidates`:
```java
if (holding.stream().anyMatch(h -> h.getSymbol().equals(c.getSymbol()))) {
    continue; // 이미 보유 중
}
```
재진입 가드도 3중이다 — #839 손절 쿨다운, #840 동일테마 차단, #835 유지경로 쿨다운.
종목 집중도 `max-symbols=5` 로 §7 '핵심 2~5개'에 부합한다.

> **결론**: `auto-trade.cron` 은 손대지 않는다. 대신 §0 의 나머지 절반인 **'점검'** 을
> 구현한다 — 거래는 이미 룰 기반인데 **점검은 구현이 아예 없다**.

## 2. 설계 — §6 주간 운영 루틴 리포트

§6 체크리스트 6항목 중 데이터로 가능한 것만 자동화하고, 불가한 것은 **'수동 확인'으로
명시**한다(없는 데이터를 추정해 채우지 않는다).

| § | 항목 | 처리 |
|---|------|------|
| 6-1 | 시장·섹터 상대강도 Top/Bottom 5 | **자동** — `daily_ohlcv` + `universe.sector` |
| 6-2 | 관찰목록 체크리스트 재적용 | **부분** — 보유분 수익률·손절선으로 대체(밸류에이션 API 호출 비용) |
| 6-3 | 이벤트 캘린더 | **수동 확인 표기** — 데이터 소스 없음 |
| 6-4 | 엔트리·손절·추적손절 가격 기입 | **자동** — 보유 포지션 |
| 6-5 | 룰대로 매수/매도 실행 | 사람의 행동 — 리포트가 재료를 제공 |
| 6-6 | 트레이드 로그 3줄 요약 | **자동** — 주간 실현손익·건수·수수료 |

### 2.1 발송 시점

월요일 **08:30 KST**(장 시작 30분 전). 주간 점검은 거래 전에 해야 재료가 되므로
장 시작 후에 보내면 늦다. 크론은 설정으로 뺀다.

### 2.2 주간 손절선은 **실제 판정 공식**을 쓴다

보유 종목의 하드/추적 손절선은 `TrailingStopCalculator.hardFloor`/`trailFloor` 를
그대로 호출해 계산한다 — 리포트가 보여주는 숫자와 봇이 실제로 쓰는 숫자가 달라지면
점검의 의미가 없다. 추적폭은 #873 의 `effectiveTrailPct`(멀티배거 완화 반영)를 쓴다.

### 2.3 섹터 상대강도

신규 쿼리 `DailyOhlcvMapper.sectorReturns(since)` — 창 내 종목별 (마지막종가/첫종가−1)을
섹터로 평균한다. **종목 3개 미만 섹터는 제외**(표본 부족으로 극단값이 나온다).
창은 §6-1 이 "상대강도"라고만 하므로 매수 게이트와 같은 `relative-strength-window-days`
를 쓴다 — 판단 기준을 한 곳으로 모은다.

### 2.4 순수/비순수 분리

`WeeklyReviewFormatter`(순수)가 문자열 조립을 전담하고, `WeeklyReviewService`(I/O)는
조회·발송만 한다. 리포트 내용 검증은 포매터 단위테스트로 한다(CLAUDE.md §1).


## 4. 인수조건 (Acceptance)

1. 거래 주기(`auto-trade.cron`)는 **변경하지 않는다**.
2. 월요일 장 시작 전 주간 리포트가 발송된다.
3. 리포트에 주간 실현손익·매매건수·수수료가 포함된다(§6-6).
4. 리포트에 보유 종목별 진입가·하드손절선·추적손절선·현재수익률이 포함된다(§6-4).
5. 리포트에 섹터 상대강도 Top/Bottom 5 가 포함된다(§6-1).
6. 데이터가 없는 항목(이벤트 캘린더)은 **'수동 확인'으로 명시**한다(§6-3).
7. 웹훅 미설정이면 조용히 건너뛴다.
8. 보유 0건·거래 0건이어도 리포트가 깨지지 않는다.

## 5. 테스트 계획

`WeeklyReviewFormatterTest`:
- 보유 2건 + 주간 거래 3건 → 모든 섹션이 포함되고 숫자가 정확
- 보유 0건 → "보유 없음" 표기, 예외 없음 (인수조건 8)
- 주간 거래 0건 → "거래 없음" 표기
- 섹터 목록이 5개 미만이면 있는 만큼만 출력
- 이벤트 캘린더 줄에 "수동 확인" 포함 (인수조건 6)

## 6. 리스크 / 되돌리기

| 리스크 | 완화 |
|--------|------|
| 리포트가 보여주는 손절선이 실제와 다름 | `TrailingStopCalculator` 를 직접 호출(§2.2) |
| 섹터 평균이 소수 종목에 끌려감 | 종목 3개 미만 섹터 제외(§2.3) |
| 월요일 공휴일에도 발송 | 무해 — 점검 리포트이고 거래를 유발하지 않는다 |
| 조회 실패로 리포트가 안 감 | try/catch 로 감싸 경고만 남긴다. 매매에는 영향 없음 |

되돌리기: `weekly-review-cron` 을 비우거나 `@Scheduled` 메서드 1개 제거.

## 7. 범위 밖

- §6-3 이벤트 캘린더 자동화 — 실적/정책/학회 일정 데이터 소스가 없다. 도입 시 별도 이슈.
- §6-2 보유분 밸류에이션 체크리스트 전체 재적용 — 종목당 외부 API 호출이라 비용이
  크다. 현재는 수익률·손절선으로 대체하고, 필요해지면 별도 이슈로 확장.
