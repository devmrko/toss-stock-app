# 설계서: 수동 정리(MANUAL) 매도 엔드포인트 (#875)

> **상태**: Approved · **작성**: [AI] Architect · 2026-10-08

## 1. 목적 (Why)

보유 3종목 중 2건이 **#869 게이트 배포(19:23) 이전**에 구 게이트(통과율 37%)로 등록된
후보에서 매수됐다.

| 종목 | 진입 | 근거 기사 |
|------|------|-----------|
| `030000` 제일기획 | 10-08 10:47 | "파격적 주주환원으로 실적 부진 돌파하는 제일기획" |
| `000020` 동화약품 | 10-08 13:03 | "동화약품, 질환인식 캠페인…다한증은 체질 아닌 관리 가능한 질환" |

둘 다 금액·규모가 제시되지 않은 홍보성 기사로, 새 기준(#865 자격 게이트)이라면
**후보 등록 자체가 안 됐다**. 사용자가 정리를 지시했다.

투자원칙 §4 에는 **"매수 근거 부실"이라는 매도 사유가 없다** — 봇이 자동으로 팔면
원칙에 없는 매도 규칙을 또 만드는 것이다(#871 에서 제거한 것과 같은 실수). 사람의
판단이 필요한 영역이므로 **수동 경로**를 둔다.

## 2. 왜 토스 API 직접 호출이 아니라 앱 경로인가

`OrderExecutor.sell` 은 아래를 한 흐름으로 처리한다.

1. 시장가 매도 주문 발행 (`TossOrderRequest.marketSell`)
2. 체결 확인 폴링 (`waitForFill`, #850)
3. 실제 체결가로 수수료·세금 계산 (`TradingFeeCalculator`, #847/#861)
4. 주문로그 저장 (수수료·세금·진입가·피크 포함, #849/#851)
5. 포지션 `EXITED` 전환 (`markExited`)
6. Discord 알림

토스 API 를 직접 호출하면 **원장이 `HOLDING` 으로 남아** 봇이 없는 포지션의 손절을
계속 감시하고, 실현손익·수수료 집계가 틀어진다. 사용자가 토스 앱에서 직접 파는 경우도
같은 문제가 생긴다 — **이 엔드포인트가 그걸 막는다.**

## 3. 설계 (What)

```
POST /api/autotrade/positions/{symbol}/sell
```

| 단계 | 조건 | 응답 |
|------|------|------|
| 1 | HOLDING 포지션에 해당 symbol 없음 | **404** |
| 2 | 그 시장이 장 마감 중 | **409** |
| 3 | 현재가 조회 실패(콜드 캐시) | **503** |
| 4 | `orderExecutor.sell(p, MANUAL, current, rationale)` | **200**(성공) / **502**(주문 실패) |

### 3.1 장 마감 중 거부가 핵심 안전장치다

`OrderExecutor.sell` 은 **시장가** 주문을 낸다. 닫힌 시장에 넣으면 거부되거나
**다음 개장 갭 가격에 체결**된다. 실거래(`dry_run=0`)에서 **체결가를 통제할 수 없는
주문을 내지 않는다** — 그래서 409 로 막고 사람이 개장 시간에 다시 호출하게 한다.

> 지정가 주문으로 바꿔 예약 체결을 노리는 방법도 있으나, "정리"는 가격 조건이 아니라
> 포지션 종료가 목적이므로 시장가가 맞다. 대신 **개장 중에만** 낸다.

### 3.2 사유 문자열

```
수동정리(피크18940→현재18820,-0.63%) 진입18940 수익-0.63%
  스탑17046(하드17046/트레일17046) 사유:사용자 지시 — 매수 근거 부실(구 게이트 등록분)
```

`ExitReason.MANUAL` 은 이미 enum 에 있고 `SellRationale` 라벨("수동매도")도 있다.
`#872` 의 note 오버로드를 재사용해 **왜 수동으로 팔았는지**를 남긴다 — 사후에
자동매도와 구분되어야 한다.

### 3.3 포지션 조회

`positionMapper.findHolding()` 결과를 메모리에서 필터링한다. 보유는 최대
`max-symbols`(5)건이라 전용 SQL 을 둘 이유가 없고, 조건이 코드에 드러나 읽기 쉽다.

## 6. 인수조건 (Acceptance)

1. 보유 중 종목을 symbol 로 지정해 `MANUAL` 사유로 매도된다.
2. 보유하지 않은 종목이면 404 이고 주문을 내지 않는다.
3. 장 마감 중이면 409 이고 주문을 내지 않는다.
4. 성공 시 포지션이 `EXITED` 로 바뀌고 주문로그에 수수료·세금이 기록된다.
5. 사유 문자열에 "수동정리"와 지시 맥락이 남아 자동매도와 구분된다.

## 7. 테스트 계획

`AutoTradeControllerTest`:
- 보유 종목 + 장중 → `orderExecutor.sell(..., MANUAL, ...)` 호출, 200
- 미보유 종목 → 404, `sell` 미호출 (인수조건 2)
- 장 마감 중 → 409, `sell` 미호출 (**인수조건 3 — 가장 중요한 가드**)
- 콜드 캐시 → 503, `sell` 미호출
- 사유 문자열에 "수동정리" 포함 (인수조건 5)

`MarketHours` 는 정적 메서드라 기존 테스트처럼 `mockStatic` 으로 고정한다.

## 8. 리스크 / 범위 밖

| 리스크 | 완화 |
|--------|------|
| 실수로 멀쩡한 포지션을 청산 | symbol 을 명시해야 하고 보유 확인 후에만 동작. 대시보드 UI 버튼은 만들지 않는다(오클릭 방지) |
| 개장 갭에 불리하게 체결 | 시장가의 본질적 성질. 정리가 목적이므로 수용하되 장중에만 주문 |

**범위 밖 — `MarketHours` 가 공휴일을 모른다.** `isOpen` 은 요일+시간만 본다. 따라서
10/09(금) 내내 "KR 장 열림"으로 판정하고, 이 엔드포인트의 409 가드도 통과시킨다.
주문은 API 단계에서 실패하고 `sell` 이 실패를 정상 처리하므로(로그·알림 후 포지션 유지)
사고는 아니지만 불필요한 시도와 오해를 만든다. **별도 이슈로 분리** — 공휴일 캘린더
데이터 소스를 정해야 하는 별개 설계다.
